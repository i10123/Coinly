# Чек-лист безопасности для ревью изменений

Ревьюер (саб-агент `security-reviewer`) обязан явно пройтись по каждому пункту,
применимому к изменённым файлам, и указать файл + строку для каждой находки.
Пункт нельзя пропускать молча — если он неприменим, так и написать: "неприменимо, т.к. ...".

## 1. Аутентификация и сессии
- Есть ли лимит попыток входа (rate limit / lockout по IP и логину)?
- Есть ли минимальные требования к паролю, хешируется ли он (bcrypt/argon2, не md5/sha1-без-соли)?
- Не палит ли ответ на неверный логин/пароль, существует ли такой email в базе?
- Для админ-панелей — есть ли 2FA или хотя бы отдельный усиленный контроль?

## 2. Контроль доступа (authorization, не путать с authentication)
- Для каждого эндпоинта, принимающего id объекта: проверяется ли, что объект
  принадлежит текущему пользователю, а не только то, что пользователь залогинен?
- Для действий, доступных только админу: проверяется ли роль на сервере,
  а не только скрытие кнопки/пункта меню на фронте?

## 3. Секреты и конфигурация
- Нет ли API-ключей, токенов, паролей от БД в коде фронтенда (том, что уезжает в браузер)?
- Нет ли секретов в git-истории / .env, закоммиченном в репозиторий?
- Используются ли переменные окружения, добавлен ли .env в .gitignore?
- Если секрет когда-либо попадал в публичный репозиторий — отмечено ли, что его нужно перевыпустить?

## 4. Инъекции и работа с пользовательским вводом
- Есть ли места, где пользовательский ввод склеивается в SQL/NoSQL-запрос строкой,
  вместо параметризованных запросов / ORM?
- Экранируется ли пользовательский текст, выводимый на страницу (риск XSS)?
  Особое внимание: `innerHTML`, `dangerouslySetInnerHTML`, `v-html` и аналоги.

## 5. Загрузка файлов
- Проверяется ли реальный тип файла по содержимому, а не по расширению?
- Переименовываются ли загруженные файлы, хранятся ли вне директории,
  откуда сервер может их исполнить?

## 6. Интеграции и вебхуки (платежи и не только)
- Проверяется ли подпись/секрет входящего вебхука?
- Защищён ли обработчик от повторной обработки одного и того же события (идемпотентность)?
- Сверяются ли сумма/валюта/статус, а не просто сам факт вызова эндпоинта?

## 7. CORS и межсайтовые запросы
- Не разрешён ли `Access-Control-Allow-Origin: *` одновременно с передачей cookie/credentials?
- Ограничен ли список разрешённых доменов конкретными значениями?

## 8. Гонки состояний (race conditions)
- Операции, где важна атомарность (списание баланса, применение промокода,
  вывод средств) — защищены ли они транзакцией с блокировкой строки
  или уникальным ключом идемпотентности?

## 9. Базы данных с публичным доступом из фронтенда (Supabase/Firebase и т.п.)
- Включены ли политики доступа (RLS в Supabase, Security Rules в Firebase)
  на всех таблицах/коллекциях, которые видны из клиента?
- Нет ли таблиц с политикой "разрешено всем"?

## 10. Зависимости и цепочка поставок
- Есть ли в проекте новые зависимости, добавленные без проверки автора/актуальности?
- Есть ли известные уязвимости в используемых версиях пакетов?

## 11. Стоимость и лимиты (denial-of-wallet)
- Есть ли лимит обращений к платным внешним API (LLM, SMS, генерация изображений)
  на пользователя в сутки и общий потолок расходов?

## 12. Промпт-инъекции и AI-инструменты (если в проекте используются агенты/LLM)
- Если проект сам вызывает LLM с пользовательским вводом — есть ли разделение
  между системными инструкциями и вводом пользователя, есть ли защита от
  переопределения инструкций через ввод?

---
Отчёт ревьюера должен выглядеть так:
```
[КРИТИЧНО] src/routes/orders.js:42 — эндпоинт /orders/:id не проверяет владельца заказа
[СРЕДНЕ] src/upload.js:15 — тип файла проверяется по расширению, не по содержимому
[OK] Проверено: CORS настроен на конкретный домен, credentials не разрешены со звёздочкой
```
Если критичных или высоких находок нет — явно написать "Критичных проблем не найдено" в конце отчёта.
